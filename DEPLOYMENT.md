# Публикация FULL CORE

Ничего не опубликовано и внешние аккаунты не подключены. Сайт — набор статических файлов; Node нужен только для сборки. По умолчанию сборка предназначена для корня домена; GitHub Pages workflow автоматически настраивает подпапку репозитория.

## GitHub Pages — автоматическая публикация

В проект уже включён `.github/workflows/deploy-pages.yml`. Он собирает и публикует статический сайт при push в `main`, а также поддерживает ручной запуск. Аккаунты пока не подключены, workflow удалённо не запускался.

1. Создайте публичный репозиторий (например `full-core`) на GitHub.
2. Загрузите **содержимое** папки проекта в корень репозитория: package.json, package-lock.json, src, public, scripts, конфигурации и `.github/workflows/deploy-pages.yml`. Не загружайте node_modules и dist. Важно: некоторые графические интерфейсы скрывают `.github`; убедитесь, что workflow действительно появился в репозитории.
3. Откройте Settings → Pages → Build and deployment → Source → **GitHub Actions**.
4. В Actions откройте **Deploy to GitHub Pages** → Run workflow → main. При следующем push в main запуск будет автоматическим. Если вкладка Actions предлагает включить workflows, включите их.
5. После успешного deploy ссылка появится в Settings → Pages и в результате workflow: `https://USERNAME.github.io/REPOSITORY/`. Не используйте адрес github.com как адрес сайта.

Workflow использует встроенный GITHUB_TOKEN с минимально необходимыми permissions. Пароли, FTP и персональные токены не нужны. Бесплатные Pages обычно доступны для публичных репозиториев; доступность приватных зависит от тарифа GitHub.

`actions/configure-pages` сообщает путь и адрес сайта сборке через SITE_BASE и VITE_SITE_URL. Шаблон работает для обычного project repository (`/full-core/`), корневого `USERNAME.github.io` и настроенного собственного домена. Код адаптирует Vite base, BrowserRouter, локальные изображения/видео, prerender, canonical и sitemap. Локальные пути в данных оставляйте `/media/file.webp`, название репозитория туда добавлять не нужно.

Все известные страницы заранее сгенерированы в отдельные каталоги с index.html. GitHub Pages открывает прямые ссылки и refresh без SPA rewrite. Для неизвестных адресов предусмотрен 404.html. Файлы .htaccess и _headers на GitHub Pages не действуют.

Если загрузили проект как подпапку, переместите его файлы в корень или задайте working-directory для команд, cache-dependency-path и путь upload artifact в workflow. Инструкция выше предполагает корень репозитория. Ветка с другим названием требует изменения `branches: [main]`.

Для проверки project-path локально (Bash): `SITE_BASE=/full-core/ npm run build`, затем `SITE_BASE=/full-core/ npm run preview`. Откройте URL с `/full-core/`. Обычный `npm run build` по-прежнему собирает для корня домена (Beget/Cloudflare).

## Перед публикацией

1. Заполните реальные работы и контакты по CONTENT_GUIDE.md. Отключите временные примеры: `demoMode: false` в site.ts. Удалите `public/media/demo/`, если образцы больше не нужны.
2. В `src/data/site.ts` задайте `url: 'https://your-real-domain.com'`. Для временного домена используйте фактический адрес Pages, после его получения пересоберите сайт. Пока домен неизвестен, canonical, og:url, og:image и sitemap намеренно отсутствуют.
3. Выполните `npm ci`, `npm run lint`, `npm test`, `npm run build`.
4. Проверьте `npm run preview`: Home, Work, фильтры, About, Contact, страницы работ, обновление браузера и неизвестный URL.

## GitHub → Cloudflare Pages

1. Создайте собственный репозиторий GitHub и загрузите исходники, включая package-lock.json. Не добавляйте node_modules, dist, .env, закрытые файлы.
2. В Cloudflare: Workers & Pages → Create application → Pages → Connect to Git. Подключите GitHub самостоятельно, выберите репозиторий и production branch (например main).
3. Framework preset: None / Vite. Build command: `npm run build`. Output directory: `dist`. Root directory: корень репозитория (если загрузили full-core как подпапку, задайте `full-core`). Environment variable: `NODE_VERSION=24`.
4. Нажмите Deploy. Домен pages.dev выдаст Cloudflare. Укажите его в site.url и отправьте изменение для повторной сборки.
5. После каждого push production-ветки Pages обновит сайт. Для локальной проверки используйте тот же lockfile и Node.

Каждый опубликованный маршрут имеет свой `index.html`, поэтому правила `/* /index.html 200` **не нужны**. Они могут подменить реальные 404 главной страницей. В корне сборки есть `404.html`: Cloudflare использует его для неизвестных путей. `_headers` задаёт заголовки безопасности и кеширование хешированных ассетов. `_redirects` намеренно отсутствует. После добавления новой работы обязательно нужна новая сборка; путь неизвестного/скрытого проекта возвращает 404.

После публикации проверьте в адресной строке прямую ссылку `/work/your-slug` и reload. Если позже добавите только клиентские маршруты, включите их в `scripts/prerender.tsx`, чтобы сохранить текущую статическую модель. Простой SPA fallback возможен отдельно (`/* /index.html 200`), но теряет корректные статические метаданные/404 для новых путей.

## Beget / Apache

1. Локально выполните `npm ci && npm run build`.
2. В файловом менеджере или по SFTP откройте document root домена (обычно public_html — проверьте в панели Beget).
3. Загрузите **содержимое** `dist`, включая `.htaccess`, `404.html`, каталоги work/about/contact/assets/media, favicon, robots и sitemap, если он создан. Не загружайте исходники и node_modules.
4. Не потеряйте скрытый файл `.htaccess`. В нём DirectoryIndex и ErrorDocument, без обязательного SPA rewrite. Провайдер должен разрешать эти директивы через AllowOverride. Если возникает 500 — посмотрите журнал Apache/поддержку Beget; уберите неподдерживаемую директиву. Не используйте Cloudflare `_redirects` как Apache-конфигурацию.
5. Включите HTTPS через панель хостинга. Проверьте все прямые ссылки и неизвестный маршрут: он должен возвращать 404 с нашей страницей.

Рекомендуется атомарная замена файлов релиза или резервная копия перед загрузкой. При ручном обновлении удаляйте старые страницы скрытых/удалённых кейсов и устаревший sitemap, иначе прежние HTML останутся доступны. Сохраняйте системные файлы хостинга. `_headers` действует на Cloudflare; Apache использует `.htaccess` и настройки хостинга.

## SEO и социальные превью

Сборка делает настоящий HTML, уникальные title/description/Open Graph для опубликованных проектов и статические ссылки. Поисковик не обязан выполнять JavaScript для чтения основного текста. Это не гарантия индексации: нужны реальный домен, доступность и качественный контент. Социальная картинка `/social-preview.png` — брендинг, не фальшивый кейс. Можно заменить собственным изображением 1200×630. После смены домена пересоберите; sitemap генерируется только при site.url. Проверьте отдачу URL и метатеги в исходном HTML на хостинге.

## Типичные проблемы

- Пустой экран / 404 ассетов: убедитесь, что загружено содержимое dist в корень домена. Для подпапки задайте SITE_BASE при сборке; GitHub Pages workflow делает это автоматически. При локальном preview используйте то же значение SITE_BASE.
- Видео недоступно: проверьте ID, privacy hash Vimeo, разрешения embed/доменов, региональные ограничения и статус Private. Facade ничего не загружает у видеопровайдера до Play.
- Старые тексты: пересоберите и обновите HTML, очистите кеш хостинга. Хешированные JS/CSS безопасно кешируются надолго.
- Нет email-кнопки: добавьте настоящий email в site.ts.
- Нет проектов: смените draft на published после добавления медиа; сборка проверяет структуру.
- Удалённый кейс всё ещё доступен на Beget: удалите его старую папку из document root.

Аналитика, домен, CV и AI-проекты подключаются позднее только с реальными данными и вашим решением. Платные сервисы для работы сайта не требуются.
